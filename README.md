# pgpreflight

[![CI](https://github.com/Aliraza777/pgpreflight/actions/workflows/ci.yml/badge.svg)](https://github.com/Aliraza777/pgpreflight/actions/workflows/ci.yml) [![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

**A pre-flight check for Postgres migrations.** Before you deploy, pgpreflight checks your pending Prisma, Drizzle or plain SQL migrations against your real database (read-only) and tells you which statements **will fail**, which will **lock a big table**, and which will **delete data**.

```bash
npx pgpreflight --db "$DATABASE_URL"
```

## Why

Linters can tell you a statement is risky in general. Only your database knows whether it will actually work:

- `SET NOT NULL` fails if **any** row is NULL.
- A unique index fails if there are **duplicates**.
- A foreign key fails if there are **orphan rows**.
- Removing an enum value fails if a row **still uses it**.
- A rewrite is harmless on 500 rows and an outage on 50 million.

Here is a real migration generated by **Prisma 7** for an everyday schema change: rename a field, make `email` required and unique, remove an enum value, add a required column. Prisma's own deploy failed with this:

```
$ npx prisma migrate deploy
Applying migration `20261023120000_daily_changes`
Error: ERROR: current transaction is aborted, commands ignored until end of transaction block
```

A second deploy then hit `P3009`, and every later deploy was blocked until the failure was resolved by hand. pgpreflight run on the same migration and database, **before** deploying:

```
$ npx pgpreflight --db "$DATABASE_URL"

pgpreflight · prisma · 1 pending migration · PostgreSQL 17.7

20261023120000_daily_changes
  prisma/migrations/20261023120000_daily_changes/migration.sql:5  ALTER TABLE "User" ALTER COLUMN "role" TYPE "Role_new" …
   WILL FAIL  ALTER COLUMN role TYPE Role_new rewrites User and its indexes while blocking all access
         ↳ 400 rows use enum values that Role_new no longer has (GUEST), so it WILL FAIL
  prisma/migrations/20261023120000_daily_changes/migration.sql:13  ALTER TABLE "User" DROP COLUMN "fullName", ADD COLUMN …
   WILL FAIL  ADD COLUMN country NOT NULL without a default fails if User has any rows
         ↳ User has rows (≈20,000), so this statement WILL FAIL
   WILL FAIL  SET NOT NULL on User.email scans the whole table while blocking all reads and writes
         ↳ 50 rows have NULL in email, so SET NOT NULL WILL FAIL

  prisma/migrations/20261023120000_daily_changes/migration.sql:22  CREATE UNIQUE INDEX "User_email_key" ON "User"("email")
```

## What it checks

| | Static (no database) | With `--db` |
|---|---|---|
| **Will it fail?** | Syntax errors, `CREATE INDEX CONCURRENTLY` inside a transaction | NULLs before `SET NOT NULL`, duplicates before unique indexes, orphans before foreign keys, rows violating a new `CHECK`, values that can't convert to a new type, rows using a removed enum value, non-empty tables for `NOT NULL` columns without defaults, **schema drift** (objects that already exist or are missing) |
| **Will it lock?** | Lock level of every statement, table rewrites and full scans | Real table sizes decide the severity; volatile defaults confirmed from `pg_proc`; **open transactions holding locks** that the migration would queue behind |
| **Will it lose data?** | `DROP COLUMN/TABLE`, `TRUNCATE`, renames done as **DROP + ADD** (what Prisma and Drizzle generate for a renamed field) | How many rows/values would be deleted |
| **Will the old app break?** | Renamed or dropped columns and tables during a rolling deploy | |

It understands how each tool runs migrations:

- **Prisma** wraps a migration file with more than one statement in a transaction, so `CREATE INDEX CONCURRENTLY` must be alone in its file. It reads `_prisma_migrations` to check only pending migrations.
- **Drizzle** (`drizzle-kit migrate`) runs **all pending migrations in one transaction**: `CONCURRENTLY` never works, and locks from the first migration are held until the last one finishes. It reads your `drizzle.config` for the output folder and migrations table.
- **Plain SQL**: pass files or folders, and use `--transaction per-file` if your runner wraps each file.

Every rule comes with a fix, such as the `NOT VALID` + `VALIDATE` pattern for constraints, a `CHECK` before `SET NOT NULL`, `CONCURRENTLY` indexes and expand/contract column changes.

## Usage

```bash
npx pgpreflight                       # static checks on the newest migration
npx pgpreflight --db "$DATABASE_URL"  # pending migrations, checked against real data
npx pgpreflight prisma/migrations/20261023120000_daily_changes
npx pgpreflight migrations/*.sql --transaction per-file
npx pgpreflight -f md                 # Markdown for a PR comment (-f json for tools)
```

| Option | |
|---|---|
| `-d, --db <url>` | Database to check against (default `$DATABASE_URL`). Prisma's `?schema=` is understood. |
| `--no-db` | Static checks only. |
| `-a, --all` | Check every migration, not only pending ones. |
| `--timeout <s>` | Time limit per data check (default 10). Checks that run out report "could not verify" instead of hanging. |
| `--blocking-after <s>` | Report open transactions older than this that hold locks on affected tables (default 30). |
| `--show-values` | Show example duplicate values (off by default, since they may be personal data). |
| `--fail-on <level>` | Exit code 1 at `fail`, `danger` (default), `warn` or `never`. |
| `-v, --verbose` | Also show informational findings. |

### In CI

```yaml
- run: npx pgpreflight --db "${{ secrets.READ_REPLICA_URL }}" -f md > pgpreflight.md
```

Post `pgpreflight.md` as a PR comment. The job fails when a migration would fail or is dangerous.

## Safety

- **Read-only.** The session sets `default_transaction_read_only = on`, so the server refuses any write. A read replica works.
- **Bounded.** Every query has a `statement_timeout` (`--timeout`) and a `lock_timeout` of 3 s.
- **Private.** It only reports counts unless you pass `--show-values`, and runs entirely on your machine.

## How it compares

[Squawk](https://squawkhq.com) is an excellent static linter with dozens of rules for risky SQL. pgpreflight adds what a linter can't know without your database: whether the statement will fail on your data, how big the tables really are, whether something is blocking right now, and how your ORM runs the migration. They work well together.

## Limitations

- **Postgres only.**
- **Table sizes come from planner statistics**, so they're estimates, as are the size thresholds (100k rows or 100 MB for a warning, 1M rows or 1 GB for danger).
- **Results are a snapshot.** Data can change between the check and the deploy.
- **Blocking sessions need visibility.** Seeing other users' sessions needs superuser or `pg_read_all_stats`.
- **Rename detection is a heuristic** based on column names.
- **App code isn't analyzed**, so "breaks the old app" findings are about the deploy pattern, not your actual queries.
